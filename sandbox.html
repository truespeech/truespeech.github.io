truespeech Sandbox

truespeech is a small language for asking precise analytical questions on top of a semantic layer, plus a queryable lexicon of contextual knowledge about the data. The runtime sits in front of the semantic layer in the data stack: database → semantic layer → truespeech.

Type a statement into the top panel. Use compute to run a metric query, register to add a lexicon entry (a region or a boundary), or check to look up what the lexicon knows about a slice. The runtime parses, validates against the semantic model, generates SQL where needed, and executes against an in-browser DuckDB. Lexicon entries are reconciled against every compute automatically — per-row, so the cells that are actually affected get flagged inline. Errors are reported with Rust-style caret diagnostics. See the language reference below.

Learn it

The full language reference — every construct, its grammar, and the trigger semantics that produce what you see in the notebook.

Regions

A region is a contiguous slice of your data — a time interval plus optional categorical constraints — over which one or more metrics are affected. The region syntax is also used by compute and check to address a slice.

# grammar
over <time-expr> [and <predicate>...]

Time expression

The first clause of over is always the metric's primary time axis, written in a small calendar mini-language:

2026                          -- the year
2026-Q1                       -- a quarter
2026-02                       -- a month
2026-02-15                    -- a day
2026-02-03 to 2026-02-10      -- a closed-inclusive range (same unit)
until 2026-Q1                 -- everything up to and including
since 2026-01-15              -- everything from that point onward
all time                      -- unbounded

Additional constraints

After the time expression, additional constraints intersect with and:

and region = 'northeast'
and region in ('northeast', 'west')
and region not in ('midwest')
and ship_date >= 2026-02-01
and ship_date in 2026-Q1                  -- in extends to time containment
and ship_date in 2026-02-01 to 2026-02-28

register region

Adds a region entry to the lexicon — a curated fact about a patch of the data, scoped to one or more affected metrics, with a natural-language description. A region triggers a result value when that value's underlying input rows came from inside the patch.

register region <name>
  impacting <metric>[, <metric>...] over <region>
  [impacting <metric>[, <metric>...] over <region>]...
  with "<description>"

Boundaries

A boundary is a cut at an instant — a metric redefinition, a pricing change, a logging-pipeline switch. Data on either side of the cut is fine in isolation, but any result value that mixes inputs from both sides conflates two regimes. Boundaries trigger per-row: an analyst who has already disambiguated the grain gets no annotation; one who hasn't is alerted that the value mixes pre-cut and post-cut data.

register boundary

Adds a boundary entry. at takes a day-form date — quarter/month forms are rejected because boundaries are instants, not intervals. before and after are mandatory and each take two strings: a short label (rendered inline in result-row notes) and a longer description (rendered in reconciliation and historical footers). with is optional and overrides the runtime-composed change-description in spanning/straddling footers. Optional and constraints scope the cut to a sub-population.

register boundary <name>
  at <date> [and <predicate>...]
  impacting <metric>[, <metric>...]
  before "<short label>" "<long description>"
  after  "<short label>" "<long description>"
  [with  "<change description>"]

Trigger semantics

The post-cut regime is treated as the operator's now — assumed normal and not annotated. The pre-cut regime is history; queries that live in it get an informational footer. Queries that span the cut get per-row regime context, and rows whose own interval straddles the cut get a harsher flag.

Query shapeTreatment
Entirely post-cut (now)silent — no flag, no footer
Entirely pre-cut (historical)informational footer composed from BEFORE/AFTER
Spans cut, every row cleanly on one sideamber warn on each row, regime label inline
Spans cut, a row straddlesred error on the straddler; warn on clean rows

A row's interval [start, end] straddles the cut at T iff start < T ≤ end. The "≤" on the right makes "T is the first day of the new regime" the natural reading — a row that starts exactly at T contains only post-cut data and does not trigger. Grain matters:

-- given REGISTER boundary aov_redef AT 2026-01-01 IMPACTING aov BEFORE … AFTER …
compute aov over 2026-Q1                                -- entirely post-cut → silent
compute aov over 2025-Q4                                -- entirely pre-cut → historical footer
compute aov over 2025-Q4 to 2026-Q1                  -- 1 row spans cut → error
compute aov over 2025-Q4 to 2026-Q1 group by quarter -- 2 rows, regime label each → warn
compute aov over 2025-Q4 to 2026-Q1 group by month   -- 6 rows, regime label each → warn

The historical-context footer wording is composed by the runtime from the registered before and after descriptions — there's no per-entry override for it, because the historical pattern is structurally "you are reading a previous regime; here's what now looks like." Override the change-description footer (shown for spanning/straddling queries) by supplying with "<sentence>".

compute

Runs a metric query over a region. Reconciled against the lexicon automatically — relevant entries (region overlaps and boundary crossings) arrive alongside the result, indexed per row so only the cells that are actually affected are flagged.

compute <metric>
  over <time-expr> [and <predicate>...]
  [group by <field>[, ...]]
  [order by <field> [asc|desc][, ...]]
  [limit <n>]

Group by

Bare grain words refer implicitly to the metric's primary time:

group by month                -- primary time at month grain
group by region               -- categorical dimension
group by ship_date:week       -- explicit time dimension with grain

check

Looks up matching lexicon entries for a region — no database hit, no metric computation. Useful for asking "what do we know about this slice of the data?" without pulling the numbers. Returns both region overlaps and boundary crossings.

check <metric>
  over <time-expr> [and <predicate>...]

Semantic model

The semantic model the runtime queries against. It defines two metrics (total_sales and average_order_value) and three dimensions (order_date, region, product_tier) over a single orders dataset. order_date is marked as the primary time dimension — that's what the bare-grain group by month and the calendar-literal forms in over bind to.

Database schema

An in-browser DuckDB-WASM instance loaded with ~200 rows of sample sales data spanning January 2025 through April 2026.

CREATE TABLE orders (
    order_id      INTEGER PRIMARY KEY,
    order_date    DATE NOT NULL,
    region        VARCHAR(50) NOT NULL,
    product_tier  VARCHAR(20) NOT NULL,
    amount        DECIMAL(10, 2) NOT NULL
);
